# 决策型竞品分析

## 这份 Skill 解决什么

帮助用户把竞品从“资料来源”变成“减少某个产品决策不确定性的证据”。

它来自“出题练习”项目中的真实经验：早期收集了大量教育产品、功能、页面和截图，却无法回答问答中的练习应该怎样设计；后期把研究改为围绕具体证据缺口组织，竞品才开始真正改变产品判断。

复用的是这次纠偏动作，不是旧项目的具体产品结论。

## 使用边界

- 先读取当前项目已有的聊天、文档、数据、用户 Case、历史判断和方案争议，再研究竞品。
- 竞品只能证明某种供给、机制或流程存在，不能单独证明当前用户有需求、设计有效或具备业务价值。
- 旧项目中的“对话＋Quiz”“先看题再选择形式”等结论不得直接套到新项目。
- 用户只是要查一个明确功能、入口或事实时，直接回答该问题，不强行展开完整框架。
- 仍处在开放探索期时，可以做广泛扫描，但必须说明扫描要建立什么样本空间，以及何时停止；不能把扫描结果伪装成产品结论。

需要回看本 Skill 的真实经验来源与具体例子时，读取 [references/examples.md](references/examples.md)。

## 核心原则

### 1. 先有待决策问题，再有竞品名单

开始前先用一句话写清：

> 本次竞品分析要帮助决定什么？

合格的问题包含两个或多个真实选项，例如：

- 先展示生成内容，还是先让用户选择使用方式？
- 保持自由对话，还是进入结构化任务？
- 采用独立页面，还是嵌入现有流程？

“看看行业怎么做”“了解竞品功能”不是决策问题。若用户尚未形成具体选择，先从当前目标、用户任务和方案争议中找出阻碍推进的未知；不要立刻搜索产品。

### 2. 竞品围绕证据缺口组织，而不是围绕公司组织

写清当前已经知道什么、还缺什么证据。证据缺口通常是：

- 不知道用户在哪一步中断；
- 不知道不同交互形态分别解决什么成本；
- 不知道某种能力如何进入完整任务；
- 不知道线上、线下或多个模块怎样衔接；
- 不知道某方案成立依赖哪些用户和产品条件。

只有可能减少这些未知的产品或流程才进入核心样本。知名但不能改变判断的产品留在扫描池或附录。

### 3. 沿同一段用户任务比较

不要一个产品看功能、另一个看页面、第三个看商业模式。先为当前项目写一条任务链，再让所有样本回答相同问题。

任务链由当前项目决定，常见观察项包括：

```text
入口与触发
→ 用户提供什么信息
→ 何时看到真实结果
→ 如何确认或修改
→ 如何开始核心任务
→ 中途遇到问题怎么办
→ 何时推进下一步
→ 如何结束与沉淀
→ 能否返回原流程或跨场所继续
```

不要把不同层次的设计混为一谈。例如研究移动体验时，分别观察任务/内容设计、输入方式、难度递进、场所分工和反馈策略。

### 4. 用对照样本解释取舍

不要寻找一个可以整体照抄的“最佳竞品”。围绕同一决策选择不同做法的样本：

- **机制样本**：把目标机制做得清楚；
- **对照样本**：采用另一种做法，帮助看清取舍；
- **边界样本**：用户、场景或商业条件明显不同，用来检查可迁移性。

样本数量由判断是否收敛决定，不设置固定数量。新样本不再改变机制理解或方案取舍时，停止继续堆产品。

### 5. 区分证据强弱

记录每项材料来自哪里：

- **强证据**：亲自完成真实流程，或有完整、连续、可复现的产品体验；
- **中证据**：官方帮助文档、完整演示、产品协议或可信的一手说明；
- **弱证据**：官网宣传、单张截图、第三方转述、仓库描述或基于页面的推测。

弱证据可以提供线索，不能支撑完整体验或效果结论。截图必须说明它具体证明哪一步，不能作为装饰。

### 6. 强制拆开事实、机制、边界和我方假设

每个重要发现使用四层表达：

1. **观察事实**：实际看到竞品怎样组织流程；
2. **机制解释**：这种做法可能降低什么成本、解决哪一段断点；
3. **迁移边界**：竞品用户、任务、频率、内容成本、商业模式与当前项目有何不同；
4. **我方假设**：基于上述证据，我们准备验证什么，而不是宣布应该照搬什么。

避免三种越级：

- “竞品有”越级成“用户需要”；
- “竞品这样设计”越级成“这种设计有效”；
- “某产品下线”越级成“这种形态不成立”。

### 7. 让竞品结论回到选择与验证

每一段研究最终都要回答：

- 它加强、削弱或推翻了哪个原有判断？
- 它让哪两个方案的取舍更清楚？
- 它仍然不能回答什么？
- 剩余未知应回到用户研究、内部数据、原型还是实验？

竞品分析的终点不是“启发”，而是减少实验空间，并明确最低成本验证。

## 标准工作流

### 第一步：读取项目，而不是从搜索开始

提取并标记：

- 产品目标与业务目标；
- 已验证的用户事实；
- 当前方案和系统约束；
- 历史上反复出现的争议；
- 尚未被证据支持的推断。

若材料混乱，先形成“事实／解释／决策主张／未知”四栏，不急着做竞品表。

### 第二步：形成决策简报

在研究前写出：

```markdown
决策：本次要决定什么？
候选：真实存在的方案选项是什么？
已知：当前项目证据已经说明什么？
缺口：为什么现在还无法取舍？
改变条件：看到什么证据会改变当前选择？
```

如果“改变条件”写不出来，说明竞品分析暂时没有明确任务。

### 第三步：定向选样本

为每个样本写一句入选理由：

> 看这个产品的哪一段流程，是为了补哪个证据缺口？

不要因为产品有名、功能多或截图好看而纳入正文。

### 第四步：建立体验证据卡

每个核心样本记录：

```markdown
## 产品／流程
- 对应决策问题：
- 用户与场景：
- 可复现入口：
- 完整路径：
- 关键页面或证据：
- 观察事实：
- 机制解释：
- 迁移边界：
- 对当前判断的影响：
- 仍需验证的我方假设：
- 证据强度：强／中／弱
```

“可复现入口”应尽量直达目标功能，并注明登录、付费、地区、设备或安装要求。无法实际体验时如实降级证据，不用宣传页填补体验空白。

### 第五步：横向形成判断

按决策问题或任务断点组织，不按公司逐个介绍。正文只保留会改变判断的差异：

- 不同做法解决了什么不同问题；
- 成立条件和代价是什么；
- 当前项目更接近哪类条件；
- 哪些设计只能作为假设。

功能全表、产品介绍和补充截图放附录。

### 第六步：明确停止条件

出现以下情况时停止继续搜产品：

- 已有样本覆盖主要对照做法；
- 新产品只是在重复已知机制；
- 当前剩余未知只能由内部数据、用户访谈或原型实验回答；
- 继续研究不会改变方案选择或验证顺序。

这时应把精力转向验证，而不是继续补行业地图。

## 常见弯路检查

发现以下信号时主动纠偏：

- 按公司逐个写，篇幅很长但没有待决策问题；
- 产品越找越多，研究范围不断从核心任务扩到相邻领域；
- 深挖了一个机制，但无法说明它会改变哪个选择；
- 链接指向官网首页，截图不能还原实际操作路径；
- 不同产品比较的是不同层次，无法横向对照；
- 把竞品供给当成用户需求或业务价值证据；
- 把合理的产品设想写成“竞品洞察”；
- 从某产品采用、增长或下线直接推断形态优劣；
- 直接写“竞品做 X，所以我们也做 X”；
- 结尾只有启发，没有方案影响、证据边界和验证动作。

## 输出方式

根据任务复杂度使用最小充分结构。完整报告建议采用：

```markdown
# 本次要帮助判断什么

## 当前已知与证据边界

## 尚未解决的证据缺口

## 为什么选择这些产品／流程

## 沿同一用户任务的对照

## 对当前产品判断的影响
### 观察事实
### 机制解释
### 迁移边界
### 我方待验证假设

## 竞品仍然回答不了什么

## 最低成本验证与停止研究建议
```

若用户只讨论一个具体判断，直接围绕该判断输出“证据—机制—边界—假设—验证”，不要机械展开完整报告。

## 质量标准

好的交付应满足：

- 开头能说清这次研究要改变哪个产品选择；
- 每个核心竞品都有明确入选理由；
- 所有样本沿同一任务链比较；
- 页面、截图和链接能支持对应结论；
- 竞品事实与我方方案假设清楚分开；
- 对迁移边界和未知有明确说明；
- 结尾能减少方案空间或给出最低成本验证；
- 删除竞品名称后，仍能读出清晰的机制和产品判断。
