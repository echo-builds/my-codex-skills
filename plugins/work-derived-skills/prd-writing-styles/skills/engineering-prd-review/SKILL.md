# 研发视角 PRD 预审

在正式研发细评前，把产品语言翻译成确定的系统行为，暴露会阻塞技术方案、排期、开发或验收的需求缺口。

目标不是代替研发出技术方案，也不是把 PRD 改成长篇规格书。目标是让正式细评聚焦少数真正的技术取舍，而不是现场发现基础需求没有定义。

## 使用边界

适合：

- 产品目标和主要方案已基本确定，已有 PRD、方案稿或较完整的需求描述。
- 用户希望知道研发会追问什么、哪里无法实现或估时、哪些异常链路没想清楚。
- 用户希望把审查意见直接补回 PRD，再进入正式细评。

不适合：

- 需求仍停留在“要不要做、为谁做、做什么”的早期探索。此时先做产品判断或需求发现。
- 用户只需要润色结构和表达。
- 用户要求评审已经完成的技术设计、接口或代码。此时按技术评审处理。

如果材料明显早于 PRD 阶段，直接说明“当前更缺产品判断，不是研发规格”，指出最少的前置问题，不要假装可以完成工程预审。

## 审查立场

- 保留产品目标，但不默认当前解法正确。
- 像一个要负责方案、估时、联调、上线和故障兜底的资深研发一样阅读。
- 先理解完整链路，再提问题；不要按通用清单机械扫射。
- 只指出会影响行为确定性、方案选择、工作量、风险、验收或后续演进的缺口。
- 不把技术实现偏好伪装成产品缺陷。
- 不凭空断言某能力一定可复用或不可复用；缺证据时标成“需研发验证”。
- 区分事实、PRD 已明确内容、合理推断和未知项。
- 给判断，不只给问题。能提出推荐默认值、简化路径或分期方案时，一并给出。

## 工作流

### 1. 完整读取材料

读取 PRD 正文、关键原型、流程图、引用规则和与本次方案直接相关的历史结论。链接不可访问时说明缺失会影响哪一部分判断，不要假设其内容。

先用自己的话重建：

- 谁在什么场景下要完成什么任务？
- 当前失败在哪里？本次改变了什么？
- 本期包含和明确不包含什么？
- 成功后的用户结果和业务结果是什么？

如果这四点无法稳定复述，优先审查产品定义，不要立即钻进边角状态。

### 2. 建立“可执行需求模型”

围绕主链路抽取：

- 参与者：用户、客户端、服务端、策略/模型、第三方、运营或人工角色。
- 核心对象：对象身份、唯一键、粒度、归属、生命周期、是否可变。
- 触发：谁感知、何时触发、进入条件、不触发条件。
- 状态：初始、处理中、成功、部分成功、失败、取消、重试、退出、恢复、历史回看。
- 输入输出：来源、格式、顺序、数量、大小、协议、错误表达。
- 持久化：存什么、存在哪里、按什么粒度、保留多久、跨端/跨版本如何恢复。

不要立刻输出这张内部模型；先用它找矛盾、空白和隐含分支。

### 3. 沿主链路做反事实追问

对每个关键节点问：

- 如果重复发生、并发发生、顺序颠倒或中途退出，会怎样？
- 如果上游只返回一部分、迟到、拒绝、超时或返回不支持的类型，会怎样？
- 如果对象被删除、移动、编辑、失效或从另一端访问，会怎样？
- 如果用户不满足权限、版本、额度、实验、网络或审核条件，会怎样？
- 如果旧数据没有新字段，或新客户端访问旧结果，会怎样？

使用最小具体反例验证规则。例如不要只说“缺少异常态”，而要说“用户在生成到第 2 张图时退出，再从历史记录进入，前两张、剩余任务和失败提示分别如何处理未定义”。

### 4. 应用研发审查维度

按需读取 [references/review-lenses.md](references/review-lenses.md)。只使用与当前 PRD 有关的维度，重点覆盖：

1. 对象、身份与数据粒度
2. 状态机、异步顺序与生命周期
3. 触发、归属与可观测性
4. 输入输出、协议与渲染能力
5. 边界、失败、权限和降级
6. 历史数据、版本兼容与迁移
7. 复用前提与跨场景依赖
8. 实验拓扑、归因与冲突
9. 性能、成本、额度与并发
10. 配置、监控、灰度、回滚与验收

### 5. 判断问题归属

每个问题必须标明谁负责闭环：

- `[产品需决策]`：用户规则、业务边界、优先级、失败体验或范围取舍没有定义。研发不应代替产品决定。
- `[研发需确认]`：复用性、技术可行性、容量、接口、实现归属等需要技术调研或方案确认。
- `[联合讨论]`：产品价值与工程代价耦合，需要共同做简化或分期。
- `[设计/数据/QA需补充]`：只有确实需要对应角色补充时使用。

不要把所有问题都抛给研发确认。能由 PRD 明确的产品规则，应要求产品先给答案。

同时给每条建议标记决策状态，避免把审查者的推荐写成既定需求：

- `必须拍板`：进入细评前必须形成唯一产品规则。
- `推荐默认`：审查者给出的低成本默认方案，需产品确认后才生效。
- `研发确认`：留到细评中由研发调研、选型或测算。

### 6. 评定严重程度与就绪度

严重程度：

- `P0 阻塞`：核心行为存在多种合理解释；关键对象/状态/责任未定义；无法可靠出方案、估时或验收；存在严重合规、资金、数据或实验有效性风险。
- `P1 重要`：不阻塞启动，但很可能造成返工、跨端不一致、线上坏例、成本失控或测试遗漏。
- `P2 建议`：能提升清晰度、可维护性或未来扩展，但不应拖住本期。

就绪度：

- `不建议进入细评`：仍有产品侧 P0，主链路无法形成单一解释。
- `有条件进入细评`：产品规则基本闭合，剩余问题主要是 P1 或需要研发在细评中做技术选择。
- `可以进入细评`：主链路、关键边界和验收口径已确定，剩余问题是真正的技术方案权衡。

不要按问题数量机械判级。一个关键状态缺失可能比十个文案问题严重。

### 7. 给出最小闭环建议

对 P0/P1 优先给：

- PRD 应补的具体规则、表格或示例。
- 推荐默认答案，以及它依赖的假设。
- 如果当前方案过重，给出保留核心价值的降级、删减或分期路径。
- 哪些问题必须在细评前解决，哪些可以留给正式细评。

不要直接替产品拍板高影响规则；把推荐方案与最终决策权分开写清楚。

## 输出格式

默认使用中文，先结论后证据。没有实质问题的章节可以省略。

主报告优先控制在 5–8 条最高价值发现。相同问题不要在多个章节重复展开；状态表、反例和技术确认只在它们能新增信息时输出。若问题很多，先给主报告，再把其余 P2 或详细状态放入附录。

```markdown
# 研发视角 PRD 预审

## 结论
- 就绪度：可以进入细评 / 有条件进入细评 / 不建议进入细评
- 一句话判断：...
- 最优先处理：列出 1–3 个真正决定就绪度的问题

## 核心发现
| 优先级 | 决策状态 | 归属 | PRD 位置/原规则 | 问题 | 为什么影响研发 | 建议补充或决策 |
|---|---|---|---|---|---|---|

## 关键链路与状态缺口
仅在状态复杂时给出场景或状态表。覆盖正常、失败、退出恢复、重复/并发、历史回看。

## 范围与分期建议
指出可以删除、降级、延后或拆分的部分，以及这样做保留了什么核心价值。

## 正式细评仍需研发确认
只保留真正属于技术方案的问题，并写明需要谁给出什么结论。

## 可直接补回 PRD
给出可粘贴的规则、表格行、验收条件或“待确认”条目。明确区分已经由 PRD 确认的规则与审查者提供的推荐默认值。

## 已具备的条件
简要说明 PRD 已经明确、无需反复讨论的部分。
```

每条发现都必须包含：

1. 它对应 PRD 的哪句话、哪一段或哪条链路。
2. 研发在细评现场会问的具体问题。
3. 不补清楚会影响什么：方案、估时、联调、成本、数据、测试或上线。
4. 产品应补什么，还是研发应验证什么。

## 质量门槛

提交前自检：

- 是否真的读懂了产品目标，而不是只做格式审查？
- 是否把“同 UI”误判成“可直接复用”？
- 是否覆盖了对象粒度、状态生命周期、归属、边界和历史兼容？
- 是否识别了异步顺序、实验冲突、额度/成本或监控回滚问题（若相关）？
- 是否区分了产品决策与技术确认？
- 是否用具体反例说明问题，而不是泛泛说“考虑异常情况”？
- 是否把 P0 控制在真正阻塞项，没有用长清单制造虚假严重感？
- 是否给出了可执行的补充方式或最小化方案？
- 审查后，研发是否能更快形成单一理解并开始方案、估时和测试设计？

如果答案是否定的，继续收敛审查意见，而不是增加更多问题。
